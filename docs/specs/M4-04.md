# M4-04: Derived cache (`cache/`, `thumbnail.png`) with `model_hash` staleness

Status: proposed

A part's `model.json` is the source of truth. Rebuilding it from scratch can take a long time on a large part, so a document may also carry derived data: one solved solid per body (`cache/body-<id>.brep`), a display mesh (`cache/display.glb`) and a preview picture (`thumbnail.png`). All of it is optional and can always be regenerated. This spec decides where each file records the `model_hash` it was built from, how `swx_io::Document` holds the cache, which crate builds each file, how the thumbnail is made before there is an app, what a reader does with a bad cache, and how the work is split and tested.

Inputs on `main`: `model_hash`, `sha256`, `Document::refresh_model_hash` and `Document::cache_is_fresh` (M4-04a, #206); `swx_io::write_glb` (M4-04b, #238); `Kernel::write_brep` / `Kernel::read_brep` (M4-04c, #243); `Kernel::tessellate`; and the `swx-qa` CPU renderer (QA-01). The container rules are in `docs/specs/FILE_FORMAT.md`.

## 1. Where the hash is recorded

**Decision: one sidecar file, `cache/index.json`, records every derived file, its own SHA-256 and the `model_hash` it was built from.** Nothing is written inside the `.brep`, `.glb` or `.png` files themselves.

Why a sidecar: the three formats have no common place for a custom field. OCCT BRep text has no metadata slot, PNG would need a `tEXt` chunk, and glTF would need `asset.extras`. A sidecar handles all three the same way, keeps the derived files byte-identical to what their writers produce, and lets a reader decide on freshness without opening the large files.

Layout, written through the canonical JSON writer (`to_canonical_json`: stable key order, 2-space indent, one array element per line):

```json
{
  "cache_format": 1,
  "entries": [
    {
      "model_hash": "sha256:9f2c…",
      "path": "cache/body-b-1.brep",
      "sha256": "sha256:41d0…"
    },
    {
      "model_hash": "sha256:9f2c…",
      "path": "cache/display.glb",
      "sha256": "sha256:77ab…"
    },
    {
      "model_hash": "sha256:9f2c…",
      "path": "thumbnail.png",
      "sha256": "sha256:0c1e…"
    }
  ]
}
```

- `cache_format` is the integer `1`. A reader that sees any other value treats the whole index as unreadable (§4).
- `entries` is a set, sorted by `path` in byte order on write (the FILE_FORMAT.md rule for sets). `path` is relative to the container root and uses `/`. It is either `thumbnail.png` or `cache/<name>`, where `<name>` has no `/` and is not `index.json`. Any other path makes that entry invalid.
- `model_hash` is the `model_hash` string (`sha256:<64 lowercase hex>`) of the model the file was built from. Each entry has its own, so files built at different times (for example a thumbnail made later by another tool) can be checked separately.
- `sha256` is `sha256:<64 lowercase hex>` of the file's bytes, computed with `swx_io::sha256`. It detects a file that was damaged or edited by hand after it was recorded.
- `thumbnail.png` stays at the container root, where FILE_FORMAT.md puts it, but is recorded in `cache/index.json` like the other derived files.

**How a reader checks an entry.** An entry is *fresh* only when all of these hold:

1. `cache/index.json` parses, has `cache_format: 1`, and the entry has valid `path`, `model_hash` and `sha256` strings;
2. the file at `path` exists;
3. `sha256` equals the hash of the file's bytes;
4. `Document::cache_is_fresh(entry.model_hash)` is true, i.e. it equals the hash of the `model.json` the writers would write now.

A file under `cache/` (or a `thumbnail.png`) that has no entry is never fresh.

**FILE_FORMAT.md:** its container tree should list `cache/index.json` and say that the hashes live there. That is a separate owner-merged PR (FILE_FORMAT.md is owner-merge only); this spec doesn't change it.

## 2. How `Document` holds the cache

```rust
pub struct Document {
    pub manifest: Manifest,
    pub model: Value,
    pub properties: Option<Value>,
    // M4-03a adds: pub attachments: BTreeMap<String, Vec<u8>>,
    /// Derived files. `None`: the document has no readable cache index.
    pub cache: Option<Cache>,
}

/// The derived files of a document, keyed by container path
/// (`cache/body-b-1.brep`, `cache/display.glb`, `thumbnail.png`).
pub struct Cache {
    pub entries: BTreeMap<String, CacheEntry>,
}

pub struct CacheEntry {
    /// The `model_hash` this file was built from.
    pub model_hash: String,
    /// The file's bytes, exactly as stored.
    pub bytes: Vec<u8>,
}

impl Document {
    /// The bytes of `path` when its entry is fresh (§1 checks 1–4), else `None`.
    pub fn fresh_cache_file(&self, path: &str) -> Option<&[u8]>;
}
```

`cache/index.json` itself is not an entry. It is built from `entries` on write (each `sha256` computed from `bytes`) and parsed on read.

**Reading** (`read_unpacked`, `read_sltwx`):

- No `cache/index.json`, or one that is unreadable (§4): `cache` is `None`. This is never an error.
- Otherwise `cache` is `Some`. It holds every entry whose file exists and whose bytes match its `sha256`, i.e. checks 1–3. Entries failing those checks are dropped silently. Check 4 (the model hash) is left to `fresh_cache_file`, so a stale cache still reads and can be reported or replaced.
- Files under `cache/` that have no entry are not read.

**Writing** (`write_unpacked`, `write_sltwx`):

- `cache: None` writes nothing: no `cache/`, no `thumbnail.png`. For the unpacked form, an existing `cache/` and `thumbnail.png` are left as they are, which is today's behavior. **A document without a cache is therefore written byte for byte as today, and the existing golden files are still reproduced byte for byte.** The implementation keeps that as a test.
- `cache: Some(c)` writes each entry's bytes at its path and `cache/index.json` from `c`. For the unpacked form it also removes the other files in `cache/`, and `thumbnail.png` when `c` has no entry for it, so the folder matches `c` exactly. In the ZIP form, entries are written after `model.json` and `properties.json`, in path order, with `cache/index.json` last.
- Writing never checks freshness. Callers that change `model` and then save should rebuild the cache or set `cache` to `None`. A stale cache that is written anyway is harmless, because §4 ignores it.

## 3. Which crate builds each file

Dependency direction (`docs/ARCHITECTURE.md`): `app → render, io → kernel, sketch → core`; `core` and `sketch` never depend on the kernel.

| Step | Crate | Why it fits the direction |
|---|---|---|
| `Cache`, `CacheEntry`, `cache/index.json` read and write in both container forms, `fresh_cache_file` | `swx-io` | Container code already lives here. Pure data; no kernel types. |
| `build_part_cache<K: Kernel>(kernel, doc, bodies, deflection_mm)`: for each `(body_id, shape)`, `Kernel::write_brep` → `cache/body-<body_id>.brep`; all bodies tessellated with `Kernel::tessellate`, merged into one mesh (indices offset per body) → `write_glb` → `cache/display.glb`; every entry gets the document's current `model_hash` | `swx-io` | `io → kernel` is allowed. It reuses the `swx-io → swx-kernel` path dependency and `occt` feature that M4-02b (#216) adds. |
| `load_body<K: Kernel>(kernel, doc, body_id) -> Option<K::Shape>`: `fresh_cache_file("cache/body-<id>.brep")` → `Kernel::read_brep`; `None` on any failure | `swx-io` | Same. |
| `thumbnail.png`: tessellate the fresh body BReps, render 256 × 256 with the existing CPU renderer, store it as an entry with the current `model_hash` | `swx-qa` (new subcommand `swx-qa thumbnail <document>`) | `swx-io` must not depend on `swx-qa`. `swx-qa` is a top-level tool crate like `swx-app`, so `qa → io → kernel` keeps the direction. It adds a `swx-qa → swx-io` path dependency, with an ADR line. |

**Where the shapes come from.** The history rebuild pipeline (M3-07) isn't on `main` yet, so `build_part_cache` takes the solved shapes from its caller, as `&[(String, &K::Shape)]` keyed by body ID. The pipeline will call it after a rebuild; until then, tests and `swx-qa` call it directly.

**Display deflection.** `build_part_cache` takes `deflection_mm`; callers pass `0.05` unless they have a reason not to (`DISPLAY_DEFLECTION_MM`). The deflection isn't recorded and doesn't affect freshness: a display mesh is for viewing only, and STL export tessellates on its own (M4-02b).

**Thumbnail before M5.** There is no app until M5, so `thumbnail.png` is optional and only `swx-qa thumbnail` makes one. It uses the same fixed isometric view and shading as `swx-qa render`, at 256 × 256 pixels (FILE_FORMAT.md). Its staleness is checked through its `cache/index.json` entry like any other file. From M5, the app's renderer (`swx-render`) may replace this; the index format stays the same.

**Third-party dependencies:** none. SHA-256 is `swx_io::sha256`, GLB is `swx_io::write_glb`, and PNG output uses `png` 0.17, which `swx-qa` already depends on and the register already lists.

## 4. Stale, missing or unreadable cache

The cache is an optimization, never a requirement. **A reader never shows an error to the user because of the cache.** In every case below, it ignores the affected file and rebuilds that result from `model.json`:

| Case | What happens |
|---|---|
| No `cache/` or no `cache/index.json` | `cache` is `None`; everything is rebuilt. |
| `cache/index.json` isn't JSON, isn't an object, has a `cache_format` other than `1`, or `entries` isn't an array | Treated as no index: `cache` is `None`. |
| One entry has a bad `path`, `model_hash` or `sha256` string | That entry is dropped; the others are kept. |
| A listed file is missing, or its bytes don't match `sha256` | That entry is dropped. |
| `model_hash` differs from the current model's (stale) | Kept in `cache`, but `fresh_cache_file` returns `None`, so it is rebuilt. |
| A fresh `.brep` that `Kernel::read_brep` rejects | `load_body` returns `None`; that body is rebuilt. |
| A fresh `thumbnail.png` or `display.glb` that a viewer can't decode | The viewer ignores it (from M5). |

Opening a document never writes anything back. A rebuilt cache is stored the next time the document is saved.

## 5. Implementation slices

The Planner opens these as issues; this spec doesn't create them. IDs continue after M4-04c.

**M4-04d: `swx-io` cache index and container support** (`size:M`; no deps). Only `crates/swx-io` changes.

- `Cache`, `CacheEntry`, `Document::cache` and `fresh_cache_file`, as in §2.
- `cache/index.json` read and written as in §1, in both container forms. Entries are sorted by path, and a second write is byte-identical.
- Every row of §4 that needs no kernel has its own test, and none of them returns an error.
- Writing a document with `cache: None` reproduces every existing golden file byte for byte.

**M4-04e: build and load body BReps and the display mesh** (`size:M`; depends on M4-04d and #216). Only `crates/swx-io` changes.

- `build_part_cache` and `load_body` as in §3, with `DISPLAY_DEFLECTION_MM = 0.05`.
- With `--features occt`: a 40 × 25 × 10 mm box as body `b-1` gives `cache/body-b-1.brep` and `cache/display.glb`. Written and read back through both forms, `load_body` gives a shape with volume 10 000 mm³ within 1e-9 relative. The GLB's accessor min/max is the box within 1e-4 mm.
- With `--features occt`: a `.brep` entry whose bytes are replaced by `"garbage"`, with its `sha256` updated to match, gives `load_body` → `None` and no panic.

**M4-04f: `swx-qa thumbnail`** (`size:S`; depends on M4-04e). Only `crates/swx-qa`, `Cargo.lock` and one appended ADR line in `docs/ARCHITECTURE.md` change.

- `swx-qa thumbnail <document>` reads an unpacked or `.sltwx` part, loads its fresh body BReps, renders 256 × 256, stores `thumbnail.png` with the current `model_hash`, and writes the document back in the same form.
- The PNG is 256 × 256, and running the command twice gives identical bytes.
- A document with no fresh body BRep exits with status 1 and a message saying the cache must be built first. It writes nothing.

## 6. Test plan for the implementation

Without OCCT (M4-04d):

1. Round trip: a document with a 3-byte `cache/body-b-1.brep`, a 1 KB `cache/display.glb` and a small `thumbnail.png` survives `write_unpacked`/`read_unpacked` and `write_sltwx`/`read_sltwx` byte for byte, and `cache/index.json` lists the entries in path order.
2. **A model edit makes the cache stale:** after `refresh_model_hash`, every entry built with the current hash is returned by `fresh_cache_file`. Change one parameter expression in `model` and none are, though `cache` still holds all of them.
3. Damaged file: flip one byte of `cache/display.glb` in the unpacked folder. `read_unpacked` succeeds, and that entry is gone while the others remain.
4. Unreadable index: `cache/index.json` set to `{`, to `[]`, and to `{"cache_format": 2, "entries": []}` each read as `cache: None`, with no error.
5. Bad entries: a `path` of `../x`, of `cache/index.json` and of `cache/a/b`, and a `sha256` without the `sha256:` prefix: each drops only that entry.
6. Unlisted file: `cache/extra.bin` with no entry isn't read. Writing the same document unpacked with `cache: Some(…)` removes it.
7. `cache: None`: every golden file is reproduced byte for byte, and an existing unpacked `cache/` is left untouched (today's behavior, still tested).

With `--features occt` (M4-04e and M4-04f): the box tests listed in §5, plus a stale-after-edit test: build the cache, change the model, and `load_body` returns `None`.

## Out of scope

- Display meshes and thumbnails for assemblies and drawings (M7–M9), per-body glTF nodes, colors and materials.
- Rebuilding the cache automatically on open or in the background; UI.
- Changes to `docs/specs/FILE_FORMAT.md` (owner-merged, §1) and any `.github/` change.
