# M3-04: Topological naming v1

Status: proposed

Persistent references to faces and edges that survive rebuilds. Fillet and chamfer (M3-05), extents to a face (M3-02), sketches on faces, and the rebuild pipeline (M3-07) all build on this. `docs/ARCHITECTURE.md` requires a regression test for every feature that references faces or edges: edit an upstream parameter, rebuild, and check that the reference still resolves.

## Problem

A kernel numbers the faces and edges of a shape in the order it happens to traverse them (`TopExp::MapShapes` in OCCT). That order depends on the operation, its inputs and the kernel version. A reference stored as "face #4" or "edge #14" therefore breaks as soon as anything upstream changes. Three concrete cases follow.

1. **A fillet edge after an extrude height change.** Extrusion1 makes a 40 × 25 plate, 10 high. Extrusion2 joins a boss of radius 5 at (20, 12.5), from z = 0 to 15, so 5 of it stands above the plate. Fillet1 rounds the circular edge where the boss meets the plate's top face. Say the kernel numbers that edge #14. The user changes Extrusion1's height from 10 to 20. The boss now ends 5 below the top face, the fuse absorbs it, and the circular edge no longer exists. The fused body is a plain box with 12 edges, so "edge #14" is out of range and Fillet1 fails with a meaningless message. With a height of 12, the boss would still stand 3 above the top, but the fuse could number its edges in a different order. Edge #14 could then be a straight plate edge, and the fillet would silently round the wrong edge.
2. **A hole face after a sketch edge is added.** Sketch1 holds a 40 × 25 rectangle (lines e1–e4) and a hole circle e5 of radius 5. Extrusion1 makes it 10 high: 4 flat sides, 1 cylindrical hole face and 2 caps. Side faces are generated in sketch-entity order, so the hole is face #4. Chamfer1 references "face #4". The user cuts a corner of the rectangle with a new line e6, so the outline has 5 sides. Face #4 is now the fifth flat side, and the hole face has moved to #5. Chamfer1 now chamfers the edges of a flat side.
3. **A face split by a later cut.** Extrusion1 makes a 40 × 25 × 10 plate. Its top face (z = 10) is face #6. Cut1 cuts a 4 wide, 3 deep groove across the full width, from x = 18 to 22. The top face splits into two faces: x from 0 to 18, and x from 22 to 40. A later sketch placed on "face #6" now lands on one of the two halves, chosen by kernel order, or on the groove's floor. The user picked one specific half, and an index cannot say which.

## Approach

**Chosen: history-based naming by generating feature, generating sketch entity and role.** This follows Kripac (1997).

- Every face that a feature creates gets a name built from:
  - the feature's stable ID;
  - a *role*: `start_cap`, `end_cap` or `side`;
  - for a side, the sketch entity whose edge swept it.
  
  The kernel reports these through its operation history:
  - in OCCT, `BRepPrimAPI_MakePrism::FirstShape` / `LastShape` give the caps;
  - `BRepBuilderAPI_MakeShape::Generated(edge)` gives the side face that each profile edge swept.
- Later features carry names forward through the kernel's *modified* and *deleted* history (OCCT: `Modified`, `IsDeleted` and `BRepTools_History` on the boolean operations):
  - a face with exactly one image keeps its name;
  - a face with several images becomes several **fragments**. Each fragment is identified by the original name, the splitting feature, and the names of the faces that bound it. This is the idea of naming by topological context from Capoyleas, Chen and Hoffmann (1996);
  - a face with no image is deleted;
  - a fragment resolves only while its splitting feature exists, is not suppressed, and still splits the face. Otherwise it is `Missing`, and the user re-picks the face, which is now whole. It never falls back to the unsplit face silently.
- An **edge** is named by the two faces it separates. When several edges separate the same two faces, it is also named by the faces its end vertices touch.
- A reference resolves only when it matches exactly one entity. Anything else is an error (see Failure handling).

Why this scheme:
- Names depend only on IDs that never change (`FILE_FORMAT.md`, rule "Stable IDs"), so they survive parameter edits that keep the topology.
- When the topology really changes, resolution fails visibly instead of drifting.

**Alternative 1: geometric matching.** Store a sample point and normal for each reference, then pick the entity nearest to them after the rebuild. It is simple, but it fails silently when the geometry moves:
- In case 1 with a height of 20, the nearest edge to the old boss circle is some plate edge, and the fillet would land on it.
- In case 3, the stored point decides the half, but only as long as the groove doesn't move past it.

It breaks the "never silently pick" rule, so it is rejected as the resolution rule. It may later help the UI suggest a repair.

**Alternative 2: full generic naming.** Capoyleas, Chen and Hoffmann (1996) name entities with a graph of generating entities and contexts, and handle splits, merges and extents generally. It is more complete, but it is a larger machine than v1 needs. v1 takes only its context idea, for fragments. Marcheix and Pierra (2002) survey the trade-offs between these families.

## Data model

ARCHITECTURE.md: `swx-core` and `swx-sketch` never depend on the kernel, and `swx-kernel` has no workspace dependencies. So names are plain data in `swx-core`, kernel indices stay in `swx-kernel`, and the code that joins the two lives in a crate above both.

**`swx-core::topo`** (new module; kernel-free and sketch-free):

```rust
/// A sketch entity, by its sketch feature and its `swx_sketch::GeomId` value.
/// Kept as a plain u32 so swx-core does not depend on swx-sketch.
pub struct EntityRef { pub sketch: FeatureId, pub entity: u32 }

pub enum Role { StartCap, EndCap, Side(EntityRef) } // grows with revolve (M3-03), sweep (M3-11)

pub enum FaceName {
    /// Created by `feature` in `role`.
    Generated { feature: FeatureId, role: Role },
    /// One piece of `of`, left after `split_by` split it; chosen by the faces it touches.
    Fragment { of: Box<FaceName>, split_by: FeatureId, bounded_by: Vec<FaceName> },
}

/// The edge between two faces (sorted), plus end faces when the pair has several edges.
pub struct EdgeName { pub faces: [FaceName; 2], pub ends: Vec<FaceName> }

pub enum TopoRef { Face(FaceName), Edge(EdgeName) }

pub enum ResolveError {
    Missing { reference: TopoRef, reason: String },
    Ambiguous { reference: TopoRef, matches: usize },
}
```

**`swx-kernel`**: `TopoKind`, `SubShape` and history types, in kernel terms only (see Kernel API).

**Resolver and naming table: a new crate `swx-model`.** It depends on `swx-core`, `swx-sketch` and `swx-kernel`, and owns feature evaluation:
- sketch regions → `ProfileLoop`, the conversion #90 left open;
- the per-feature naming table: for every face of the body after each feature, its `FaceName`;
- `resolve(&TopoRef) -> Result<SubShape, ResolveError>`.

A new crate needs an ADR, so slice M3-04f opens it as a `needs-human` PR. Until the owner decides, the crate name and placement here are a proposal.

## Kernel API

These are additions to `swx-kernel`. Indices are 0-based positions in the shape's own `TopExp::MapShapes` map, and they are valid only for that shape.

```rust
pub enum TopoKind { Face, Edge, Vertex }
pub struct SubShape { pub kind: TopoKind, pub index: usize }
pub enum Operand { A, B } // A: the target or only input; B: the tool body

/// Per-input images and generated sub-shapes of one operation.
pub struct OpHistory {
    /// Input sub-shape → its images in the result (empty: deleted).
    pub modified: Vec<(Operand, SubShape, Vec<SubShape>)>,
    /// Input sub-shape → result sub-shapes generated from it.
    pub generated: Vec<(Operand, SubShape, Vec<SubShape>)>,
}

pub struct ExtrudeHistory {
    pub start_cap: SubShape,
    pub end_cap: SubShape,
    /// Edge of the input face → the side face it swept.
    pub sides: Vec<(SubShape, SubShape)>,
}

trait Kernel {
    // existing methods …
    fn sub_shape_count(&self, s: &Self::Shape, kind: TopoKind) -> Result<usize, KernelError>;
    /// Sub-shapes of `kind` adjacent to `of` (faces of an edge, edges of a face, edges of a vertex).
    fn adjacent(&self, s: &Self::Shape, of: SubShape, kind: TopoKind)
        -> Result<Vec<SubShape>, KernelError>;
    /// `make_face`, plus each (loop, segment) → the face's edge built from it.
    fn make_face_tracked(&self, plane: &Workplane, outer: &ProfileLoop, holes: &[ProfileLoop])
        -> Result<(Self::Shape, Vec<Vec<SubShape>>), KernelError>;
    fn extrude_tracked(&self, face: &Self::Shape, extent: Extent)
        -> Result<(Self::Shape, ExtrudeHistory), KernelError>;
    fn boolean_tracked(&self, op: BooleanOp, a: &Self::Shape, b: &Self::Shape)
        -> Result<(Self::Shape, OpHistory), KernelError>;
}
```

OCCT mapping:
- `adjacent`: `TopExp::MapShapesAndAncestors`.
- `make_face_tracked`: the shim already builds one edge per segment, in loop order.
- `extrude_tracked`: `BRepPrimAPI_MakePrism::FirstShape`, `LastShape` and `Generated(edge)`. With the offset move from #90, the start cap is the moved input face.
- `boolean_tracked`: `BRepAlgoAPI_BooleanOperation::Modified`, `Generated` and `IsDeleted`.

## File format

References are stored in `model.json` with string IDs, following `FILE_FORMAT.md`: stable IDs, no indices and no display names. A sketch entity is written as `"<sketch id>/<entity id>"`.

```json
{ "id": "ft-c410", "type": "fillet", "name": "Fillet1",
  "edges": [
    { "kind": "edge",
      "faces": [
        { "feature": "ft-91c2", "role": "end_cap" },
        { "feature": "ft-b7e0", "role": "side", "entity": "sk-2d11/e1" }
      ] }
  ],
  "radius": { "param": "r1" } }
```

A fragment is written as follows:

```json
{ "kind": "face",
  "fragment_of": { "feature": "ft-91c2", "role": "end_cap" },
  "split_by": "ft-5a90",
  "bounded_by": [ { "feature": "ft-5a90", "role": "side", "entity": "sk-77c3/e2" } ] }
```

When the faces alone don't single out an edge, the reference adds `"ends": [ … ]`, a list of face names. Readers keep fields they don't recognize, as the `FILE_FORMAT.md` versioning rules require, so later roles round-trip.

## Failure handling

Resolution returns exactly one entity, or an error:
- `Missing`: the name matches nothing. Causes: the generating sketch entity was deleted, the face was consumed by a boolean, or the edge's two faces no longer touch.
- `Ambiguous`: the name matches several entities, for example a fragment whose `bounded_by` faces match both halves.

The resolver **never picks one silently**.

What the user sees:
- The feature that holds the reference goes into an **error state**:
  - its feature-tree entry shows an error mark;
  - its message names the reference in words and the reason, for example: "Fillet1: edge between Extrusion1 end cap and Extrusion2 side (e1) no longer exists: the two faces don't touch after Extrusion1 changed", or "Sketch2: placement face Extrusion1 end cap was split by Cut1 into 2 faces; pick one".
- The feature is skipped:
  - the body shows the result of the previous feature;
  - later features that use its body rebuild from that result;
  - later features that reference its faces fail in turn with `Missing`.
- Nothing is deleted. Once the user re-picks the reference or undoes the edit, the feature rebuilds.

The UI for re-picking a reference is out of scope here.

## Test scenarios

Each test builds a model, edits one thing upstream, rebuilds, and checks the reference.

1. `extrude_height_keeps_cap_and_side_refs`: a plate 40 × 25 × 10 with a fillet on the edge between `end_cap` and `side(e1)`. Here e1 is the line from (0, 0) to (40, 0). Change the height to 12. The edge resolves to the top front edge: y = 0, z = 12, x from 0 to 40.
2. `sketch_dimension_keeps_side_ref`: a chamfer on face `side(e2)` of the plate. Change the rectangle's width dimension from 40 to 50. The face still resolves, and its normal is still +X.
3. `added_sketch_entity_keeps_hole_ref` (Problem case 2): a reference to the face `side(e5)` (the hole). Add the corner line e6. The reference resolves to the cylindrical face of radius 5, not to a flat side.
4. `reordered_feature_keeps_ref`: two cuts of different sizes, and a fillet on an edge of the second cut's side face. Swap the order of the two cuts. The edge still resolves to the same geometry: the midpoint matches within 1e-6.
5. `split_face_fragment_ref` (Problem case 3): a reference to the fragment of `end_cap` split by Cut1 and bounded by `Cut1 side(e2)`. It resolves to the half from x = 22 to 40. Move the groove to x = 10..14. The reference still resolves, now to the half from x = 14 to 40.
6. `deleted_entity_reports_missing`: delete sketch entity e1. A fillet on `side(e1)` returns `Missing`. The feature is in the error state with a message, and the body equals the result of the feature before it.
7. `absorbed_boss_reports_missing` (Problem case 1): raise the plate to 20. The fillet on the boss/top edge returns `Missing`, not some other edge.
8. `ambiguous_fragment_reports_ambiguous`: a fragment reference with an empty `bounded_by` on a face split into 2 returns `Ambiguous { matches: 2 }`.
