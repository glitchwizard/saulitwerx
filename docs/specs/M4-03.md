# M4-03: STEP import as a dumb solid feature

Status: proposed

A user brings in geometry made elsewhere as a STEP file (ISO 10303-21 exchange structure, AP242 or AP203/AP214). The result is a solid with no parametric history: a **dumb solid**. It appears in the feature history as one feature, `Imported1`, and later features can build on its body like on any other. This spec fixes what that feature stores, how it rebuilds, how it fails, how units are read, which crate does what, and how the implementation is tested.

Inputs on `main`: `Kernel::import_step(&Path)` and `Kernel::export_step` (`crates/swx-kernel/src/lib.rs`, round-trip tested by M1-05), the `swx-core` document model, and the `.sltwx` container in `swx-io` (`docs/specs/FILE_FORMAT.md`).

## 1. What the feature stores

**Decision: the STEP file's bytes are embedded in the document. The embedded bytes are authoritative.**

- On import, the file's bytes are copied unchanged into the container as `attachments/<feature-id>.step`. `FILE_FORMAT.md` already reserves `attachments/` for embedded data.
- `model.json` gets one feature entry:

```json
{ "id": "ft-3b10", "type": "import_step", "name": "Imported1",
  "source": {
    "attachment": "attachments/ft-3b10.step",
    "sha256": "sha256:9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08",
    "original_name": "bracket.step"
  },
  "op": "new_solid", "suppressed": false }
```

- `attachment` is the only thing read at rebuild time.
- `sha256` is the SHA-256 of the embedded bytes, written in the same `sha256:<hex>` form as `manifest.json` → `model_hash`. It is an integrity check, not an identity: a mismatch is an error (§3).
- `original_name` is the file name the user picked, without its directory. It is for display only and is never opened again.
- Not stored: the original path. A path breaks when the document or the STEP file moves, and the document would no longer be self-contained. Linking to an external file that updates on change is a later item (out of scope).
- `op` is `new_solid` only in this slice. `suppressed` works as for every feature.
- One feature makes one body: `bodies` gets `{ "id": "b-…", "created_by": "ft-3b10", "name": "<original_name without extension>" }`. A STEP file with several solids becomes one body holding them all (the kernel already returns all roots as one shape). Splitting into several bodies is a later item.
- The attachment follows the usual container rules: the packed form deflates it, the unpacked form keeps it as a plain file, and both forms must round-trip it byte for byte.

## 2. How the feature gets its shape after a load

**Decision: imported again from the embedded bytes at rebuild time.**

- Rebuild reads `attachments/<feature-id>.step`, checks its SHA-256 against `source.sha256`, writes it to a temporary file (`std::env::temp_dir()`, removed afterwards), and calls `Kernel::import_step` on it. The `Kernel` trait stays path-based; no new kernel method is needed.
- The derived cache (M4-04, `cache/body-<id>.brep`) may be used instead, under the same `model_hash` staleness rule as every other body. There is no special cache path for imported solids, and the cache is never the only copy.
- An imported feature has no inputs and reads no parameters, so dirty propagation never rebuilds it because of an edit elsewhere. It rebuilds only when its own attachment changes (a later "replace file" command) or on a full rebuild.

## 3. Errors and feature state

**When the user imports a file** (nothing is added to the document on any of these):

| Case | Message |
|---|---|
| File missing or unreadable | ``cannot read STEP file `<path>`: <OS error>`` |
| File does not start with `ISO-10303-21;` (after optional whitespace) | `` `<path>` is not a STEP file (ISO 10303-21 header missing)`` |
| The kernel rejects it | ``STEP import of `<path>` failed: <kernel message>`` |
| The kernel returns a shape with zero volume | `` `<path>` contains no solid`` |

**When the document is loaded and rebuilt** (the document still opens; the feature fails):

| Case | Message |
|---|---|
| Attachment missing | ``Imported1: embedded STEP file `attachments/ft-3b10.step` is missing`` |
| SHA-256 mismatch | ``Imported1: embedded STEP file `attachments/ft-3b10.step` is damaged (sha256 does not match)`` |
| The kernel rejects it | `Imported1: STEP import failed: <kernel message>` |

A failed feature stays in the history with its error, produces no body, and makes every feature that uses its body fail as a downstream error, the same as any other failed feature. The user can delete it, or replace its file once that command exists. Loading never silently drops the feature or its attachment: a reader that writes the document back keeps both unchanged (FILE_FORMAT.md, *Versioning*).

## 4. Units

- A STEP file declares its length unit in its global unit context, as an `SI_UNIT` (for example `SI_UNIT(.MILLI.,.METRE.)`) or a `CONVERSION_BASED_UNIT` (for example `'INCH'` defined as 25.4 mm), per ISO 10303-41 (*Fundamentals of product description and support*, units of measure).
- The OCCT STEP reader converts every length to its session unit when it transfers the shape. The session unit is set by the `xstep.cascade.unit` parameter and defaults to millimetres (OCCT *STEP Translator* user guide, "Reading STEP", parameter `xstep.cascade.unit`). The shim (`swx_occt_import_step`) leaves the default, so an imported shape is always in millimetres, which is the kernel's internal unit and the unit `export_step` writes.
- So a part modelled in inches imports at its true size: a 1 in cube becomes a 25.4 mm cube. The document's `manifest.json` → `units` is a display preference and is not changed by an import.
- A file whose unit context is missing or unreadable is imported as millimetres, which is the reader's own fallback. This is not an error.
- The implementation adds a test that proves the conversion (§6, test 3) and a doc comment on `import_step` that states it, citing the two sources above.

## 5. Crate ownership

Dependency direction (`docs/ARCHITECTURE.md`): `app → render, io → kernel, sketch → core`; `core` and `sketch` never depend on the kernel.

| Step | Crate | Why it fits the direction |
|---|---|---|
| `FeatureKind::ImportedSolid { attachment: String, sha256: String }`: no inputs, no parameters, so history order and dirty propagation work unchanged | `swx-core` | Plain data; no kernel types. |
| `attachments/` read and written in both container forms (`Document` gains `attachments: BTreeMap<String, Vec<u8>>`, sorted by name on write) | `swx-io` | Container code already lives here. |
| `import_step` entries in `model.json` read and written through the canonical writer | `swx-io` | Same. |
| `embed_step(doc, path)`: header check, kernel trial import, attachment, feature and body entries; `rebuild_imported(kernel, doc, id)`: hash check, temp file, `import_step` | `swx-io` | `io → kernel` is allowed. `swx-io` gains a path dependency on `swx-kernel` with an `occt` feature that forwards to `swx-kernel/occt`, the same pattern `swx-qa` uses. |
| `import_step` itself (unchanged) | `swx-kernel` | Already exists. |

The rebuild pipeline that walks the whole history (M3-07) is not on `main` yet, so `rebuild_imported` is called directly by tests and, later, by that pipeline. No `core → kernel` or `core → io` edge is added.

**Third-party dependencies:** none. The SHA-256 function is `swx_io::sha256`, which M4-04a (#206) implements in `swx-io` from NIST FIPS 180-4 with no new dependency; the implementation issue depends on #206 and reuses it. The temporary file uses `std` only.

## 6. Test plan for the implementation

Without OCCT (run by the default `cargo test --workspace`):

1. `attachments/` round-trip: a document with a 3-byte and a 100 KB attachment survives `write_unpacked`/`read_unpacked` and `write_sltwx`/`read_sltwx` byte for byte; names are written in sorted order.
2. `import_step` feature JSON: write, then read, gives the same `source` fields, and the canonical writer's output is byte-identical on a second write.
3. Errors with no kernel needed: a missing attachment, a SHA-256 mismatch (one byte flipped) and a file without the `ISO-10303-21;` header each give the exact message from §3.
4. `swx-core`: `FeatureKind::ImportedSolid` reports no inputs and no parameters, and editing an unrelated parameter does not mark it dirty.

With `--features occt` (CI job `swx-kernel (occt)`):

5. **Round trip.** Build a 40 × 25 × 10 mm box, `export_step` it, `embed_step` it into a new part, `write_sltwx`, `read_sltwx`, `rebuild_imported`. Volume 10 000 mm³ and bounding box (0, 0, 0)–(40, 25, 10), both within 1e-6 relative. The embedded bytes equal the exported file, and `source.sha256` matches them. Repeat through the unpacked form.
6. **Units.** In the exported STEP text, replace `SI_UNIT(.MILLI.,.METRE.)` with `SI_UNIT($,.METRE.)` (metres). The imported box is 40 000 × 25 000 × 10 000 mm, volume 1e13 mm³, within 1e-6 relative.
7. **Kernel failure.** A file with a valid header and a truncated body gives `STEP import of … failed: …` at import and adds nothing to the document.

## 7. Implementation issue

One `size:M` issue, created by the Planner (this spec does not create it):

**M4-03a: STEP import as an embedded dumb solid feature** — `Depends on: #206`.

Acceptance criteria, in outline:

- `swx-io` reads and writes `attachments/` in both container forms, byte for byte (tests 1).
- `swx-core` has `FeatureKind::ImportedSolid` with no inputs and no parameters (test 4).
- `model.json` reads and writes `import_step` features as in §1 (test 2).
- `embed_step` and `rebuild_imported` behave as §1–§3 say, with the exact messages of §3 (tests 3, 7).
- With `--features occt`: the round-trip test (5) and the units test (6) pass with the stated tolerances.
- `import_step` gets a doc comment on unit conversion citing §4's sources.
- An ADR line in `docs/ARCHITECTURE.md` records the new `swx-io → swx-kernel` path dependency and its `occt` feature.
- No new third-party dependency.
- QA report (FACTORY §6b) with a `swx-qa render` of the round-tripped box.

## Out of scope

- Linking to an external STEP file that updates when it changes; "replace file".
- Transforming (moving, rotating) the imported solid at import time.
- Join, cut or intersect operations for an imported feature (`op` other than `new_solid`).
- Splitting a multi-solid file into several bodies, and importing assemblies as components.
- Face and edge references on imported solids (persistent naming, M3-04, has no generating sketch entity for them).
- Changes to `docs/specs/FILE_FORMAT.md`: the `import_step` feature schema is added there by a separate owner-merged PR, as that file requires.
- Any UI (M5).
